# BaizePaw 开发流程总纲

> 所有开发必须遵循此流程，不可跳过。

---

## 一、流程概览

```
┌─────────────────────────────────────────────────────────────┐
│  1. 想法产生                                               │
│     ↓                                                      │
│  2. 方案讨论（形成 ADR）                                     │
│     ↓                                                      │
│  3. 方案确认                                               │
│     ↓                                                      │
│  4. 编写实现计划（Plan）                                    │
│     ↓                                                      │
│  5. 实现开发                                               │
│     ↓                                                      │
│  6. 测试验证                                               │
│     ↓                                                      │
│  7. 提交代码 + 写 DevLog                                   │
└─────────────────────────────────────────────────────────────┘
```

---

## 二、详细步骤

### 1. 想法产生

任何时候都可能产生新想法（新功能、优化点、问题修复）。

**记录位置**：`docs/devlog/TODO.md`（随手记录，不拘格式）

---

### 2. 方案讨论（形成 ADR）

**触发条件**：有新功能要添加、有技术方案需要决策

**文档格式**：写入 `docs/adr/XXX-name.md`

**ADR 结构**：
```markdown
# ADR-XXX: 功能名称

## 状态
待讨论 / 已通过 / 已废弃

## 背景
为什么需要做这个

## 方案
具体的方案描述

## 待讨论
需要确认的问题列表

---

**请审阅此方案，有需要调整的地方吗？**
```

**关键点**：
- 先问用户：这功能想解决什么问题？
- 给用户提供 2-3 个方案选项
- 说明每个方案的优缺点
- 用户确认后，把 ADR 状态改为"已通过"

---

### 3. 方案确认

用户阅读 ADR，确认方案或提出修改。

**确认后**：
- 把 `## 状态` 改为 `已通过`
- 删除 `## 待讨论` 章节
- 列出 `## 实现清单`（checkbox 列表）

---

### 4. 编写实现计划（Plan）

**文档位置**：`docs/plans/YYYY-MM-DD-feature-name.md`

**Plan 结构**：
```markdown
# 功能名称实现计划

## Goal
一句话描述目标

## Architecture
架构说明

## Task N: 任务名称
**Files:**
- Create: `path/to/file.py`

- [ ] Step 1: 具体操作
- [ ] Step 2: ...
```

---

### 5. 实现开发

**执行方式**（根据任务复杂度选择）：

**方式 A：Subagent-Driven（推荐）**
- 每个 Task 派一个 subagent
- Task 完成后 review
- 适合多任务、并行开发

**方式 B：Inline Execution**
- 在当前 session 直接执行
- 适合简单任务、快速验证

---

### 6. 测试验证

**单元测试**：
```bash
PYTHONPATH=. pytest -v
```

**手动测试**：
```bash
./baize
# 输入测试指令
```

**验证清单**：
- [ ] 单元测试全过
- [ ] 手动功能测试通过
- [ ] 没有明显 bug

---

### 7. 提交代码 + 写 DevLog

**提交规范**：
```bash
git add -A
git commit -m "feat: 添加功能名称"
git push
```

**DevLog 记录**：
写入 `docs/devlog/vX.X-feature-name.md`

**DevLog 结构**：
```markdown
# vX.X 功能名称

> 日期：YYYY-MM-DD
> 目标：解决什么问题

## 实现过程

### 步骤 1: 做什么
- 做法
- 遇到的问题
- 如何解决

## 踩过的坑
记录这个版本踩过的坑和解决方案

## 下一步
- [ ] 功能 A
- [ ] 功能 B
```

## 四、流程检查清单

每次开发新功能前，检查：

- [ ] 想法已记录到 `docs/devlog/TODO.md`
- [ ] 方案已写成 `docs/adr/XXX.md`
- [ ] 方案已获确认（状态：已通过）
- [ ] 已编写 `docs/plans/YYYY-MM-DD-xxx.md`
- [ ] 实现清单已完成
- [ ] 测试验证通过
- [ ] 代码已提交
- [ ] DevLog 已写入

---

## 五、关键原则

1. **先方案后开发**：不写代码先写方案，用户确认后再动手
2. **文档即代码**：所有决策、方案、过程都要写进文档
3. **小步提交**：每个功能单独提交，方便回溯
4. **测试驱动**：改完必须验证，不只改不验
5. **过程可见**：让学习者能看到每一步是怎么走的
