# ADR-008: Agent 系统事件层

## 状态
已通过（作为 Pipeline Plugin 系统的一部分实现）

## 背景

当前 Agent 内部只有一层循环：调 LLM → 执行工具 → 调 LLM → ...，直到 LLM 不再输出工具标记。

这在简单任务中够用，但长程任务中存在几个问题：

1. **工具执行产生的系统事件没有去处**——文件截断、结果超出限制、网络重试等系统行为，只能混在工具结果里发给 LLM，分类不清
2. **Agent 无法自主推进多步骤任务**——比如"文件太大只读了前 1000 行"，系统有能力继续读，但没有机制自动发起"继续读取"
3. **系统事件的归属模糊**——是工具执行结果的一部分，还是独立的系统行为？当前混在一起

## 方案

系统事件层作为 Pipeline Plugin 系统的一部分实现。详见 ADR-009 的整体架构设计。

核心机制：
- Pipeline 在每次 LLM 迭代中注册固定的检查点（`before_iteration`、`after_tool`、`after_iteration`）
- 系统事件插件在这些检查点捕获事件（截断、超限、超时），通过事件队列输出
- Plugin 不直接操作历史，只通过 context 读写、通过队列发送事件

## 系统事件类型

| 事件 | 触发条件 | 系统层响应 |
|------|---------|-----------|
| 文件被截断 | `file_read` 或 `grep_file` 结果超过限制 | 自动补发完整读取请求，或通知 LLM |
| 结果过多 | `grep_file` 只显示了前 50 条 | 记录"还有 X 条未显示"，系统层可发起扩展搜索 |
| 工具执行超时 | `subprocess.run(timeout=30)` 触发 | 记录超时，通知 LLM 重试或放弃 |
| 网络重试 | LLM API 调用重试成功 | 记录但不告知 LLM（透明） |
| Token 水位告警 | 累计对话达到阈值 | 触发自动存档或提醒用户 |
